HashiCorpAgents

HashiCorp Vault community node for BizFirst.Ai — KV secrets, token lifecycle, dynamic-secret leases, and health/seal-status checks as workflow steps, against your own tenant-operated Vault server.

What it does: The HashiCorp node (hashicorp) wraps a tenant-operated HashiCorp Vault server's REST HTTP API as BizFirst.Ai workflow operations across four resources — secrets, token, lease, and system — 18 operations in total. There is no BizFirst-hosted Vault; every call is pointed at the tenant's own server via vaultAddress.

Single-use AppRole secret_id not yet supported: if a tenant's AppRole is configured with secret_id_num_uses = 1 (HashiCorp's own recommended hardening pattern), this node's cache-then-reauth design works until the cached client token expires, then fails every subsequent execution with HASHICORP_AUTH_FAILED. Use secret_id_num_uses = 0 (unlimited) until this is resolved.

Authentication

Every authenticated operation carries vaultAddress, authMethod (token | appRole), and credentialID, plus optional appRolePath (default approle) and namespace (Vault Enterprise):

  1. authMethod: "token" — a pre-issued Vault client token, resolved via ICredentialResolver.GetBearerTokenAsync.
  2. authMethod: "appRole" — a role_id/secret_id pair (stored as a BizFirst PasswordRecord), exchanged for a client token via POST /v1/auth/{appRolePath}/login. The exchanged token is cached per credentialID until shortly before its TTL expires.
  3. system.health and system.sealStatus skip credential resolution entirely — they are unauthenticated by design.

Configuration

There is no fixed Vault server baked into application settings — every call carries its own vaultAddress, since Vault is self-hosted per tenant:

{
  "resource": "secrets",
  "operation": "read",
  "vaultAddress": "https://vault.internal.example.com:8200",
  "authMethod": "token",
  "credentialID": 42,
  "mount": "secret",
  "path": "myapp/db-creds"
}

Writing a secret uses the data field for the flat key/value map (not secretData):

{
  "resource": "secrets",
  "operation": "write",
  "vaultAddress": "https://vault.internal.example.com:8200",
  "authMethod": "appRole",
  "credentialID": 42,
  "mount": "secret",
  "path": "myapp/db-creds",
  "data": { "username": "svc_app", "password": "s3cr3t" }
}

Roadmap

Open decision on single-use AppRole secret_id support (see warning above). Beyond that: a transit (encrypt/decrypt) resource is flagged as a Phase 2 candidate, not committed scope; and there is no live integration testing yet against a real Vault instance (OSS, Enterprise, or HCP Vault Dedicated) — everything today is verified by compiling and by direct comparison against HashiCorp's official API docs. Deliberately not planned: token/create (admin operation, out of scope), Kubernetes/LDAP/Okta/JWT/cert auth methods (only Token and AppRole are supported), and response caching for Secrets reads (a security anti-pattern, not a gap).
